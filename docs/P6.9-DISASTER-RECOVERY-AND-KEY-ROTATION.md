# P6.9 加密 D1 备份、恢复演练与无停机密钥轮换

P6.9 只增强控制面安全和可恢复性，不部署数据节点、不扩大用户或落地能力，也不增加 KV 计数写入。

## 1. D1 备份边界

`.github/workflows/d1-backup.yml` 当前只允许手动触发。配置并离线保存
`D1_BACKUP_ENCRYPTION_KEY` 后，先连续完成一次备份和恢复演练，再考虑增加定时触发。

备份流程：

1. GitHub Runner 使用固定的 Wrangler 版本导出生产 `opus8cf-db`；
2. 导出文件只存在于 Runner 的临时目录；
3. Node WebCrypto 使用 PBKDF2-SHA256（310,000 次）派生 AES-256-GCM 密钥；
4. 只上传带认证的 `.opus8bk` 密文及 SHA-256 文件，Artifact 保留 14 天；
5. 工作流结束后 Runner 临时目录销毁，仓库、日志和 Artifact 都不包含明文 SQL。

备份密钥要求：

- 独立生成至少 32 字符的随机值，不能复用 JWT、HMAC、管理员密码或落地配置密钥；
- 保存到 GitHub Actions Secret `D1_BACKUP_ENCRYPTION_KEY`；
- 另存一份到离线密码管理器。GitHub Secrets 无法回读，丢失该密钥等同于丢失备份；
- 不要写入仓库、Issue、Actions 日志或普通聊天消息。

## 2. 恢复只进入隔离数据库

恢复脚本禁止覆盖 `opus8cf-db`，只能写入显式创建且为空的
`opus8cf-recovery-*` 数据库：

```bash
wrangler d1 create opus8cf-recovery-20260729
export OPUS8_RESTORE_CONFIRM=restore:opus8cf-recovery-20260729
bash infra/scripts/d1-backup.sh restore \
  opus8cf-d1-20260729T000000Z.opus8bk \
  opus8cf-recovery-20260729
```

执行前还必须通过环境变量提供 Cloudflare 账号、API Token 和
`D1_BACKUP_ENCRYPTION_KEY`。脚本会验证：

- 目标名不是生产数据库；
- 目标符合固定的 recovery 命名规则；
- 确认字符串与目标完全一致；
- 目标数据库存在且没有业务表；
- 密文的 AES-GCM 认证标签和 SQL 基本结构都有效。

也可以手动运行 `d1-recovery-drill` 工作流，填写成功的 `d1-backup` Run ID、隔离数据库名和完全一致的
`restore:<database>` 确认字符串。工作流只下载加密 Artifact、校验 SHA-256，并在目标不存在时创建指定的
recovery 数据库；仍由相同脚本拒绝生产库和非空目标。

恢复后先只读核对关键表数量、抽样用户和落地机记录。生产切换不由脚本或工作流自动执行，必须另行制定变更窗口和回滚方案。

## 3. 无停机密钥轮换模型

控制面支持三组可选的过渡密钥：

| 当前 Secret | 过渡 Secret | 兼容行为 |
|---|---|---|
| `JWT_SECRET` | `JWT_SECRET_PREVIOUS` | 新登录签发当前密钥 JWT，已有 JWT 可继续验证 |
| `NODE_HMAC_SECRET` | `NODE_HMAC_SECRET_PREVIOUS` | 控制面接受新旧节点签名，并按请求所用密钥加密落地配置包 |
| `LANDING_CONFIG_KEY` | `LANDING_CONFIG_KEY_PREVIOUS` | 新凭据使用当前密钥，旧凭据可读取并批量重加密 |

控制面向节点推送策略失效时先使用当前 HMAC；节点尚未切换时，再使用过渡 HMAC 重试。旧密钥不会输出到 API 或日志。

`GET /api/operations/key-rotation` 仅对管理员开放，返回：

- 三类过渡密钥是否已配置；
- 落地机凭据分别由当前/过渡密钥加密的数量；
- 无法解密的记录数量。

`POST /api/operations/key-rotation/landings` 会先解密检查全部记录。只要有一条不可读，整批迁移就会在写入前失败；检查全部通过后才分批重加密。

## 4. 推荐轮换步骤

### 4.1 JWT

1. 把旧 `JWT_SECRET` 保存为 `JWT_SECRET_PREVIOUS`；
2. 为 `JWT_SECRET` 设置新的独立随机值；
3. 手动运行 `deploy-control`，选择 `retire_previous_secret=none`；
4. 验证新登录和现有会话均可访问；
5. 等待最长 JWT 有效期 24 小时；
6. 删除 GitHub Secret `JWT_SECRET_PREVIOUS`；
7. 再运行 `deploy-control`，选择 `retire_previous_secret=jwt`。

### 4.2 落地配置密钥

1. 把旧 `LANDING_CONFIG_KEY` 保存为 `LANDING_CONFIG_KEY_PREVIOUS`；
2. 设置新的 `LANDING_CONFIG_KEY`；
3. 运行 `deploy-control`，选择 `none`；
4. 确认 key-rotation 状态中的 `unreadable=0`；
5. 调用落地凭据迁移端点；
6. 确认 `previous=0`、`current=total`，并测试每台落地机；
7. 删除 GitHub Secret `LANDING_CONFIG_KEY_PREVIOUS`；
8. 运行 `deploy-control`，选择 `landing-config`。

### 4.3 节点 HMAC

HMAC 轮换需要逐台重新部署数据节点。当前合规门禁为 `provisioning=0` 时不得启动该轮换：

1. 取得 Cloudflare 针对当前数据面形态的书面许可；
2. 把旧 HMAC 保存为 `NODE_HMAC_SECRET_PREVIOUS`，再设置新的当前 HMAC；
3. 先部署控制面；
4. 单台 canary 节点切换，验证心跳、UUID、准入、用量和落地配置；
5. 逐台完成所有节点；
6. 确认所有节点只使用当前密钥；
7. 删除 GitHub Secret `NODE_HMAC_SECRET_PREVIOUS`；
8. 运行 `deploy-control`，选择 `node-hmac`。

绝不能在仍有节点使用旧 HMAC 时选择 `node-hmac` 或 `all`。

## 5. 验收

- `pnpm --filter @opus8-cf/control-plane test:d1-backup`
- `pnpm --filter @opus8-cf/control-plane test:key-rotation`
- `pnpm --filter @opus8-cf/control-plane test:signature`
- `pnpm --filter @opus8-cf/control-plane test:integration:local`
- 手动备份产生的 Artifact 只有 `.opus8bk` 和 `.sha256`
- 隔离恢复数据库可查询，生产数据库没有被写入
- 部署冒烟输出 `OK smoke-key-rotation-state unreadable=0`
