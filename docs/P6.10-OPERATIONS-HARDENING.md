# P6.10 运营硬化：灾备、身份审计、声明式节点与数据治理

P6.10 只验证控制面和部署架构，不改变 `infra/compliance-policy.json` 的决策，不放宽新增节点/用户门禁，
也不提供流量伪装、用途隐藏或规避 Cloudflare 审查的能力。P6.11 用户门户与 P7 计费不在本阶段范围内。

## A. 灾备与 strict 迁移门

- `d1-backup.sh` 现在会保留并净化 `wrangler d1 list` 的失败原因，针对限流和临时错误做有界重试，
  不再因管道重定向产生无诊断失败。
- `backup-freshness.yml` 每六小时检查 `d1-backup` 最近成功运行；超过 26 小时会创建或更新 GitHub Issue，
  恢复后自动关闭。该检查只读 Actions 元数据，不接触备份密钥或备份正文。
- `strict-promotion-gate.mjs` 只有在全部已启用节点同时满足下列条件时允许 strict：独立凭据、无旧凭据回退、
  健康、心跳不超过 20 分钟、独立传输路径、凭据 canary 至少 72 小时。
- `deploy-nodes` 选择 `transport_mode=strict` 时会在创建登记任务之前执行该门禁；不达标时不会调用 Cloudflare 写接口。
- 所有工作流的 `checkout`、`setup-node` 和备份上传 Action 已升级到官方 Node 24 版本并继续固定完整提交 SHA，
  消除 GitHub Runner 对旧 Node 20 Action 的弃用告警，同时保持供应链不可漂移。

## B. 最小权限自动化与管理员审计

节点部署不再使用 `ADMIN_PASSWORD` 登录控制面。它使用独立的 `CONTROL_AUTOMATION_SECRET` 对请求签名，控制面只在以下端点
接受该身份：

- `GET /api/nodes`
- `POST /api/node-enrollments`
- `DELETE /api/node-enrollments/:id`

签名绑定固定身份、五分钟时间窗、随机请求 ID、方法、完整 pathname/query 和正文 SHA-256。变更请求 ID 会通过 D1
`INSERT OR IGNORE` 原子消费，窗口内重放会失败。默认唯一允许身份为 `github-node-deploy`；该密钥不能访问用户、落地机、
合规、密钥轮换或其他管理员接口。

所有成功的管理员变更和自动化登记变更写入 `admin_audit_log`。只记录身份、认证方式、方法、URL pathname、状态码、
请求 ID 和时间，不记录查询参数、请求正文、JWT、注册令牌、密钥或原始 IP。管理站“运营总览”显示最近审计事件。
共享密码登录另由 Workers Rate Limiting binding 按匿名化来源限制为每分钟 10 次；生产要求 binding 存在，调用异常时失败关闭。
管理站 JWT 从持久化 `localStorage` 迁移到当前浏览器标签会话的 `sessionStorage`，关闭标签后不再长期保留令牌。

首次发布前生成独立的至少 32 字符随机值，将同一个值保存为 GitHub Actions Secret
`CONTROL_AUTOMATION_SECRET`。`deploy-control` 会把它安装为控制面 Worker Secret `AUTOMATION_HMAC_SECRET`。
不得复用管理员密码、JWT、节点根密钥、落地配置密钥或备份密钥。

## C. 声明式账号和节点接入

`infra/accounts.json` 是部署拓扑的唯一声明源。每个账号包含 Secret 名称引用和 `nodes` 数组；仓库中不存账号 ID、
API Token 或根域名明文。`node-deploy-matrix.mjs` 在工作流启动时验证账号别名、节点 ID、归属前缀、地区、部署后缀、
Secret 引用、重复项和目标是否存在，然后生成最小矩阵。

增加一个账号/节点的步骤：

1. 在 Cloudflare 创建该账号专用、最小权限且可撤销的 API Token；不要复用其他账号 Token。
2. 在 GitHub Actions Secrets 新增 Account ID、API Token、根域名三个值，名称使用新的唯一后缀。
3. 在 `infra/accounts.json` 增加一个 account 对象，引用三个 Secret 的名称，并在 `nodes` 中声明 node ID、region；
   node ID 必须以 `<account-alias>-` 开头。
4. 运行质量门验证清单；然后在现有合规策略明确允许该账号和节点后，才能以 `operation=provision` 运行 `deploy-nodes`。

第 4 步保留了已有的默认拒绝门禁。仅修改清单或增加 Cloudflare 账号不能绕过书面许可、拓扑白名单或资源预算检查。

## D. 可观测性、SLO 与数据保留

- 控制面开启抽样日志（5%）和追踪（1%）；边缘数据面不启用请求日志，避免把订阅令牌、独立传输路径或连接元数据写入日志。
- 控制面每六小时运行数据维护：过期租约、25 小时前的匿名 IP 指纹、已应用用量事件、健康事件、过期登记任务、
  已解决告警、管理员审计和自动化 nonce 按各自保留期删除。
- 累计 `usage` 聚合不由维护任务删除，避免改变用户额度与历史总量语义。
- `GET /api/operations/slo` 和管理站展示节点健康/心跳、凭据隔离及最近一次数据维护状态。

保留期：匿名 IP 指纹 25 小时，已应用用量事件 2 天，节点健康事件 7 天，过期未用登记任务 30 天，已完成登记任务和
已解决告警 90 天，管理员审计 180 天；自动化 nonce 到期即可删除。

## 发布顺序

1. 配置 `CONTROL_AUTOMATION_SECRET`，运行 `deploy-control`，确认 schema、定时任务、SLO 和审计接口可用。
2. 在管理站确认 SLO；首次数据维护运行前 `retentionCurrent=false` 属于预期，最长约六小时后应转为 true。
3. 仅对一个已有节点运行 `deploy-nodes` 的 `maintenance + canary`，确认自动化审计身份为 `github-node-deploy`。
4. 验证全部现有节点后再逐台维护。strict 仍须满足 72 小时门禁；P6.10 不自动切换持久模式。
5. 手动运行一次 `d1-backup` 后检查 `backup-freshness` 能保持健康；恢复演练仍只允许隔离数据库。

若未配置新 Secret，控制面部署预检和新的节点部署工作流都会失败关闭；管理员交互登录和现有运行节点不受影响。
